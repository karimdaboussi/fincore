CHAPTER 01 / THE BIG PICTURE

One website. Three responsibilities.

Architecture is the way a system divides work, connects its parts, and controls who is allowed to do what. FinCore separates the user interface, banking rules, and stored records.

Think of a bank branch

The frontend is the service desk: it shows information and collects instructions. The backend is the staff following banking procedures: it identifies you, checks your permissions, and decides whether to act. The database is the durable record: it stores accounts, balances, and completed transactions.

What your project actually is

A React single-page application communicates with one Spring Boot application over a REST API. Spring Boot uses PostgreSQL. The Java application has several internal layers, but those layers are parts of one backend deployment, rather than separate microservices.

Your local system map

Click a part to see its exact role. Vite is shown separately because it is the development server and API proxy; the React interface itself executes in your browser.

The browser is the presentation layer

It executes the React JavaScript bundle, renders forms and tables, and sends HTTP requests. It never opens a database connection. A visible balance is a copy of data returned by the API, not the bank's authoritative record.

The authority rule

The frontend helps users make valid requests. The backend decides whether those requests are allowed. PostgreSQL protects stored data even if application code makes a mistake. Disabling a button is useful UX, but it is not authorization.

Why separate the layers?

  • Change the interface independently. A new dashboard design does not require changing the transfer rules.
  • Reuse the API. Swagger, the React website, Postman, or a future mobile app can call the same endpoints.
  • Test rules without a browser. A service unit test can check insufficient funds directly.
  • Keep data across restarts. PostgreSQL stores records independently of a browser tab or Java process.
Logical architecture versus running processes

Three tiers describes responsibilities: presentation, application logic, and data. It does not mean that exactly three programs must appear in Task Manager. Locally you have a browser, a Node/Vite process, a Java process, and PostgreSQL processes.

Inside the backend, controllers, services, repositories, and entities are code layers. They are not HTTP servers on different ports. A call from TransactionController to TransactionService is an ordinary Java method call inside the same application.

In a production hosting design, a static server or CDN would serve the built frontend, and a reverse proxy would route /api to Spring Boot. That is a deployment option; the current Compose file packages the backend and database, not the React frontend.

CHAPTER 02 / CONNECT THE PIECES

What happens after you click?

Follow one request from a button to a database result. The interface changes only after it receives information; the server's response connects the user experience to the stored banking state.

A customer sends $250

POST /api/v1/transactions/transfer
  1. Collect and review the instruction

    MoneyDialog.tsx collects a destination account number and an exact amount string. The user reviews the details before confirming.

  2. Send a signed-in request

    api.ts adds the Bearer token and Idempotency-Key. Vite forwards the same /api/v1 path to the backend.

  3. Validate identity and banking rules

    Spring Security validates the JWT. The controller extracts its subject. TransactionService checks ownership, approval, status, funds, and the UTC daily limit.

  4. Commit the financial work together

    The service locks the relevant rows, changes both balances, and saves one transfer record in the same database transaction.

  5. Return a receipt and refresh

    The API returns a safe transaction DTO. React shows the receipt and reloads account/activity data.

Do not confuse these identifiers

A deposit route uses accounts.id. Customer approval uses customers.id. A transfer uses the recipient's account_number. Transaction details use bank_transactions.id. These values may sometimes look similar, but their meanings are different. Never guess an account ID from a customer ID.

CHAPTER 03 / JAVA APPLICATION LAYER

The backend is the decision maker.

FinCore's backend is a Java 21 / Spring Boot 3.5 application. Embedded Tomcat receives HTTP requests. Spring creates and connects the application's objects, Spring Security verifies identity, and services coordinate work through repositories.

Security filter chain→Controller + validation→Service→Repository / JPA→PostgreSQL

1. Controllers translate HTTP into method calls

A controller owns routing and request/response handling. @RestController makes returned objects HTTP response bodies. @RequestMapping, @GetMapping, and @PostMapping connect URLs and HTTP methods to Java methods. Jackson reads JSON into request records and writes response records back to JSON.

From TransactionController.javaRequest identity comes from the JWT
@PostMapping("/transfer")
public TransactionView transfer(
    @AuthenticationPrincipal Jwt jwt,
    @RequestHeader("Idempotency-Key") String key,
    @Valid @RequestBody Transfer r) {
  return transactions.transfer(
      Long.valueOf(jwt.getSubject()),
      r.destinationAccountNumber(),
      r.amount(),
      key);
}

@Valid applies the Jakarta constraints in Requests.java. For example, the amount must be present, positive, and have at most 17 integer digits and 2 fractional digits. A malformed body fails before it reaches the main banking logic. Services still perform their own checks because they may be called from tests or other Java code.

ControllerResponsibility
AuthControllerRegistration and login
CustomerControllerThe authenticated user's profile and name update
AccountControllerThe authenticated user's account and balance
TransactionControllerTransfers, withdrawals, own history, authorized details

2. Services own business rules

A controller should not implement balance arithmetic or decide whether a frozen account can send funds. Those decisions live in services. AuthService creates customer/account records and issues tokens. CustomerService handles identity lookup, administrator checks, profiles, application decisions, and account states. AdminService returns paginated directories and system aggregates. TransactionService exposes named deposit, withdraw, and transfer operations, sharing a private move implementation inside their transaction boundary. Entity fields are private and accessed through getters and setters.

The exact order inside TransactionService.move()
  1. Normalize the amount using BigDecimal.setScale(2, UNNECESSARY) and validate the idempotency key.
  2. Lock the acting customer's row. Check the administrator role for deposits, or customer role and APPROVED status for withdrawals/transfers.
  3. Resolve source/destination IDs. The service avoids loading account balances before it locks account rows.
  4. Look for a completed record with the same actor and idempotency key. Return the original if its type, amount, source, and destination match; otherwise reject with 409.
  5. Reject a transfer to the same account.
  6. Sort account IDs and acquire pessimistic write locks in ascending order.
  7. Check account states, recipient approval, available funds, the daily outgoing transfer total, and destination balance capacity.
  8. Capture one timestamp for both the UTC daily-window calculation and the transaction's creation time.
  9. Subtract from the source when applicable, add to the destination when applicable, create the transaction record, and map it to a response DTO.
  10. On normal completion of the proxied transactional method, commit the database transaction. An unchecked exception triggers rollback.

The controller does not get a successful service return until the surrounding transaction interceptor has completed its commit attempt. If commit fails, that is an error path rather than a committed success.

3. Repositories express database access

CustomerRepository, AccountRepository, and TransactionRepository are interfaces extending Spring Data JPA repository types. Spring creates runtime implementations. Standard operations such as findById, save, and count are supplied by the framework; named methods and @Query declarations describe additional queries.

From AccountRepository.javaJPQL and a lock request
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select a from Account a where a.id=:id")
Optional<Account> lockById(Long id);

The query above uses JPQL: Account and a.id refer to Java entity mappings. Hibernate translates that intent into PostgreSQL SQL and a compatible row-locking operation. It is not JavaScript, and it is not a separate network call between repositories and services.

4. Entities map Java objects to database rows

Customer, Account, and Transaction are JPA entities. @Entity marks persistent types; @Table names their tables. IDs are generated using identity-style database columns. @OneToOne connects an account to its customer. A transaction has two @ManyToOne account associations: source and destination.

A loaded entity inside the persistence context is managed. Hibernate can detect changes to its fields. That is why source.setBalance(source.getBalance().subtract(amount)) does not need a separate accounts.save(source) call in this service: dirty checking schedules the update for flush. Saving the new transaction schedules its insertion; with identity-generated IDs an INSERT may occur earlier than final commit.

Flush, commit, and DTOs are different ideas

Flush sends pending persistence operations to the database within the current transaction. Commit makes that transaction's changes durable and visible under the database's transaction rules. A flush is not a commit; a later failure can still roll the work back.

A DTO is a deliberately selected API shape, not a managed entity. Views.CustomerView omits the password hash. Views.AccountView exposes account details without the customer entity graph. Views.TransactionView exposes account numbers, rather than returning nested JPA relationships.

spring.jpa.open-in-view=false keeps the persistence context out of the entire web rendering lifecycle. Services should load/map the information they need within their transaction. This reduces accidental late database access during JSON serialization.

5. Dependency injection wires the layers

Spring discovers components such as @Service and @RestController. A constructor lists the objects a class needs, and Spring supplies them. For example, TransactionService receives its three repositories. This is constructor injection: dependencies are explicit and tests can substitute Mockito implementations.

Application configuration also supplies beans: SecurityConfig creates the BCrypt encoder, JWT signing/verification objects, and the HTTP security chain. OpenApiConfig describes Swagger authentication and stable page serialization. AdminBootstrap can create an initial administrator from environment variables.

6. Authentication is not authorization

Authentication: who are you?

Login reads the customer record by normalized email and verifies the password with BCrypt. A successful login issues an HS256-signed JWT containing an issuer, subject, issue time, and expiry. The subject is the user's database ID. The token lasts one hour.

Authorization: may you do this?

Services read the user's role and status from the database. Administrator routes delegate to administrator checks. Customer operations derive ownership from the authenticated user, and transaction detail access checks whether the customer was involved.

  • The JWT in this project does not contain a role claim. UI role selection comes from the login/profile response; backend role enforcement uses database records.
  • The security chain requires authentication for protected routes. The code does not implement administrator protection by URL-based hasRole rules; business services perform those checks.
  • The frontend does not send arbitrary sender IDs. Knowing another customer's account ID does not grant access to spend from it.
  • BCrypt is one-way password hashing, not reversible password encryption. Login compares a candidate against the stored hash.
  • Logout clears the frontend's in-memory session. There is no server token-revocation list or refresh-token endpoint in this implementation.
How @Transactional works, and what it does not promise

Spring's usual transaction mechanism wraps a service bean with a proxy. A call entering through that proxy begins or joins a transaction, invokes the method, then commits or rolls back. Default rollback applies to unchecked exceptions; checked exceptions need explicit rules when rollback is intended.

Calling another method on the same object does not pass through that proxy again. Keep meaningful transactional boundaries on externally called service methods. FinCore's controller-to-service calls use injected Spring-managed objects.

@Transactional groups work. It does not, by itself, prevent two requests from making decisions using the same old balance. FinCore also requests explicit row locks. The optimistic @Version field is an additional mechanism, not a substitute for the coordination used here.

Framework explanation: Spring: using @Transactional

7. Errors become controlled HTTP responses

ApiException carries a status and business message. GlobalExceptionHandler converts business, validation, malformed-input, data-integrity, lock, and access errors into HTTP Problem Details responses. Spring Security handles authentication failures through its own filter machinery; those responses are not guaranteed to have the same JSON body as controller advice errors.

Illustrative business errorA stable, readable response
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Insufficient balance",
  "instance": "/api/v1/transactions/withdraw"
}

A frontend error message is the last step of this chain. The rule itself belongs in the service, the status communicates its outcome, and the interface explains what the user should do next.

CHAPTER 04 / THE BROWSER APPLICATION

The frontend turns decisions into an experience.

React manages the interface, TypeScript describes expected data, Vite serves/builds the app, and a small API client connects the browser to Spring Boot. The frontend presents banking state; it does not own the actual money.

3. Data fetching has a lifecycle

  1. Choose a data key

    A view includes relevant state, such as filters, page number, or refresh revision, in the key passed to useLoad.

  2. Enter loading state

    The helper clears the previous result and starts its asynchronous loader.

  3. Request the required API data

    The initial workspace loads the current profile, either the customer's account or admin statistics, and up to 100 recent transactions.

  4. Render success or error

    Resolved data becomes the visible screen. Failure becomes ErrorPanel with an explicit retry action; live failures do not silently replace the account with demo data.

  5. Ignore obsolete results

    Cleanup marks an old load inactive. Its result cannot overwrite a newer view after unmount or a key change.

Cleanup and request cancellation are not identical

The current useLoad cleanup ignores the result of an obsolete request. It does not itself abort that HTTP request. Separately, api.ts uses an AbortController to stop waiting after 30 seconds.

An aborted browser wait does not prove a financial transaction was cancelled on the server. Spring Boot may already have committed it. That is why uncertain money-moving responses keep their idempotency key for a deliberate retry.

A manual refresh or a completed action increments the workspace revision. This is a simple reload mechanism, not a shared query cache. The app has no React Query, Redux, or persistent client database.

4. One API client carries consistent requests

api.ts centralizes fetch behavior. Every route is prefixed with /api/v1. Signed-in requests include Authorization: Bearer ...; JSON bodies get the content type; financial requests include Idempotency-Key. The client parses JSON, turns error responses into ApiError, and triggers sign-out when a protected request receives 401.

From the transfer confirmation flowAmounts remain strings in the request

A TypeScript type such as request<Transaction> helps the developer work with the expected result. It does not validate arbitrary JSON at runtime. The client currently relies on the backend contract and small compatibility helpers such as normalizePage.

5. Why the browser does not need database credentials

The browser calls a relative URL on its own origin, for example http://localhost:5173/api/v1/accounts/me. Vite forwards /api to http://localhost:8081 with the path intact. This is a server-side proxy operation; the browser does not make a direct cross-origin request to PostgreSQL or need a JDBC URL.

The API_TARGET setting configures the Vite server. It is not a database secret and does not give the browser database access. The current backend does not need broad CORS permissions for this local same-origin arrangement.

6. Forms separate intention from confirmation

FORM→REVIEW→WAITING→RECEIPT

The first step validates the amount and destination. The review step displays what will happen before sending a request. Confirming performs the actual API call. Busy controls prevent duplicate clicks. A successful response displays a receipt and refreshes backend data. There is no local optimistic subtraction from the authoritative account balance.

If a response is uncertain, editing/closing that dialog is disabled so the user can retry the same payload with the same key. The key lives in memory for that dialog; it is not a durable recovery mechanism across browser reloads. After losing an uncertain dialog, the transaction history must be checked before creating a new instruction.

7. Precision, dates, and pagination

  • Money inputs: lib.ts converts a decimal string into BigInt cents for exact validation. For example, "0.29" becomes 29n, avoiding floating-point arithmetic for that validation.
  • Money limits: the client checks per-operation maximums and displayed funds for early feedback. The backend rechecks the committed state and aggregate daily limit.
  • Dates: choosing November 17 as the end date becomes an API boundary of November 18 at 00:00 UTC, because the API end bound is exclusive.
  • Pagination: history requests normally load 20 records per page; the API caps page size at 100. Responses use {content, page: {number, size, totalElements, totalPages}}.
  • Compatibility: normalizePage also accepts the earlier flat PageImpl response format.
  • Scope: directory search filters the loaded page, CSV exports the visible page, and dashboard summaries use at most the latest 100 transactions. Those are not full-history analytics.
Exact write validation does not make every JavaScript number exact

JavaScript's ordinary number has finite precision. The current API emits monetary response numbers, the frontend types balances as number, and the display helper converts values through Number. Extremely large balances may therefore lose cent-level precision in the browser even though PostgreSQL and Java preserve their stored decimal values.

A future improvement would serialize monetary response fields as decimal strings and format/compare them without converting through binary floating point. The current BigInt input checks and BigDecimal backend writes should not be described as complete arbitrary-precision display support.

8. Presentation, accessibility, and the demo boundary

styles.css provides the component/layout foundation; theme.css supplies the reference-inspired navy/gold identity. Fonts are self-hosted. Phosphor supplies icons, and Radix Dialog supplies modal semantics, focus handling, and Escape behavior. The responsive interface uses a desktop sidebar, a mobile drawer, and frequently used mobile bottom tabs.

demo.ts supplies invented records. Entering a demo is an explicit session choice, not a fallback for failed authentication. Mutation controls are disabled in demo mode. The backend is still the security authority for real sessions; a frontend demo flag has no power to bypass server checks.

CHAPTER 05 / DURABLE DATA

The database is the lasting record.

PostgreSQL holds the customer identities, account balances, and successful financial records. Java objects and browser state can disappear when programs stop; committed database rows remain until deliberately changed or removed.

6. Customer status and account status are independent

Application lifecycle

PENDING→APPROVEDorREJECTED

Only pending customer applications can be decided through the current API. Approved or rejected decisions are not reversed by another application-decision endpoint. Pending/rejected users can sign in and inspect information, but financial operations remain restricted.

Account lifecycle

ACTIVE↔FROZEN→CLOSED

Administrators can freeze/unfreeze accounts. A zero-balance active or frozen account may be closed. Closed accounts cannot reopen through this API. Approval alone does not override an account freeze.

Frozen accounts cannot withdraw or participate in transfers in either direction. Administrator deposits may credit a frozen account if its customer is approved. Closed accounts cannot perform financial operations. A recipient must be approved before receiving funds.

7. Decimal storage, timestamps, and indexes

Why NUMERIC(19,2), BigDecimal, and BigInt all appear

NUMERIC(19,2) allows 19 total decimal digits, including two digits after the decimal point. Its maximum positive stored value is 99,999,999,999,999,999.99. It preserves decimal values in PostgreSQL. Java BigDecimal keeps the backend arithmetic decimal too.

The API explicitly rejects fractional cents by requiring exact scale conversion without rounding. SQL storage scale alone is not the same validation rule: direct inserts into a NUMERIC column can round excess fractional digits. That is why the service's UNNECESSARY rounding rule matters.

Frontend BigInt cents validate entered amounts exactly. They do not replace Java's transaction logic or PostgreSQL's persisted values. The display limitation for very large JavaScript response numbers is explained in the frontend chapter.

What TIMESTAMPTZ and UTC mean here

PostgreSQL stores an absolute timestamp value; its session timezone affects textual display. TIMESTAMPTZ does not preserve the original human-entered timezone name. Java uses Instant, and the API represents instants with UTC-compatible ISO timestamps.

History uses an inclusive lower bound and exclusive upper bound. Daily outgoing totals use a UTC day calculated from the same timestamp later stored on the transaction. The date on a user's computer may differ from that UTC date around midnight.

How the indexes help the access patterns

The migration creates composite indexes on (source_account_id, created_at) and (destination_account_id, created_at). They can help queries that find one account's records over time. A history query may use both sides because an account can send or receive.

Primary keys and uniqueness constraints also provide indexed access paths. Examples include customer email, account number, account ownership, transaction reference, and the actor/idempotency-key pair. The last pair is important for both retry lookup and duplicate prevention.

An index is not a guarantee that every query uses it. PostgreSQL chooses a plan based on the query and available statistics; scanning a tiny table may be cheaper. Use real query plans and measurements before tuning a growing system.

8. Flyway owns schema evolution

src/main/resources/db/migration/V1__initial.sql creates the schema. At startup, Flyway connects using the configured datasource, checks its migration history, and applies missing migrations. It records migration metadata in flyway_schema_history.

Hibernate is configured with ddl-auto: validate. It checks that mappings fit the schema rather than recreating tables. A normal restart does not reset balances or rerun registration. To change an already-used schema, add a new versioned migration such as V2__add_new_field.sql; do not casually rewrite a migration that has already been recorded.

9. Stored data and backups are different responsibilities

Committed rows outlive the Java process and browser sessions. In Compose, the PostgreSQL data directory uses a named Docker volume, postgres-data. That is persistence across normal container recreation, not an independent backup strategy. A running website, a database volume, and a recoverable backup are different operational concerns.

CHAPTER 06 / WHY BANKING OPERATIONS STAY CONSISTENT

Make the failure cases visible.

A correct transfer needs more than subtracting one number and adding another. It must handle failure, concurrent requests, and retries without leaving contradictory records.

Atomicity: the entire financial change is one unit

Suppose account A has $1,000 and account B has $200. A $250 transfer must finish with $750 and $450, plus one successful record. If a failure occurs before commit, both original balances must remain and no successful record may be committed.

Conceptual transaction boundaryTeaching SQL, not an exact Hibernate execution trace
BEGIN;
-- lock actor and relevant account rows; validate all rules
UPDATE accounts SET balance = balance - 250.00 WHERE id = :source;
UPDATE accounts SET balance = balance + 250.00 WHERE id = :destination;
INSERT INTO bank_transactions (...);
COMMIT;

-- If the transaction fails before commit:
ROLLBACK;

Hibernate chooses the actual flush order. The guarantee comes from all related writes using the same database transaction, not from executing these conceptual lines in precisely this displayed order.

Isolation and locks: two requests must not spend the same funds

Without coordination

Two withdrawals each read $1,000 and each decide that $750 is affordable. If both act on that old view, the application can make an incorrect financial decision even if each individual request is transactional.

With this project's locks

The service serializes financial requests for the same actor and locks account rows. One $750 withdrawal commits, leaving $250. The waiting request checks the updated balance and is rejected. It cannot treat the earlier $1,000 read as authoritative.

No custom transaction isolation level is selected in the application. PostgreSQL normally defaults to READ COMMITTED, where separate statements can observe different committed snapshots. FinCore explicitly coordinates its critical decisions with locks; the transaction annotation alone is not that coordination.

Actor locks serialize retries from one identity. Account locks protect balance decisions even when another actor, such as an administrator depositing funds, touches the same account. Sorted account IDs reduce opposite-direction transfer lock cycles. They are a discipline for these code paths, not a blanket promise that any future code can never deadlock.

Database background: PostgreSQL transaction isolation

Why optimistic @Version exists alongside pessimistic locks

Account.version is annotated with @Version. Hibernate includes a version condition when updating a managed account and advances that version. A stale version means another change occurred, so an update cannot silently overwrite the current row.

Pessimistic locking asks the database to coordinate access before financial decisions. Optimistic versioning detects incompatible writes through the entity mapping. FinCore primarily uses the former for coordinated transfers and daily-limit checks, with the latter as an additional safeguard.

Idempotency: a retry is not a second instruction

A network response can disappear after a transfer commits. Sending another request with a new key could represent a new transfer. Retrying with the same actor, key, and payload lets the backend locate and return the original record.

  • Same actor + same key + matching operation: return the previous transaction without moving funds again.
  • Same actor + same key + changed amount/type/accounts: reject with a conflict.
  • Different actors: keys are scoped separately by the composite uniqueness rule.
  • Failed, rolled-back operation: no completed transaction is stored to consume the key.
The two protections solve different problems

Atomicity prevents partial financial writes. Idempotency prevents repeating an already completed instruction. Row locks coordinate simultaneous decisions. A complete financial operation needs all of these ideas together.

Where the daily limit fits

After locking the source, the service sums that account's outgoing TRANSFER amounts for the UTC day and adds the requested amount. A result above $5,000 is rejected. Deposits and withdrawals do not count toward that specific outgoing-transfer aggregate. The sum is checked under coordinated access, rather than only against a frontend number.

What the design intentionally does not model

The record table stores completed simulated operations. Failed attempts are not persisted as pending/failed transaction rows. There are no separate ledger postings, payment-provider settlement stages, or reconciliation jobs. A complete audit/event ledger would be an additional design rather than something already hidden inside these three tables.

The backend startup sequence

  1. Start the JVM and Spring application

    Java reads the packaged JAR, loads application classes/dependencies, and builds the Spring application context.

  2. Resolve configuration and initialize data access

    Environment variables supply database credentials and JWT settings. HikariCP manages database connections. Flyway checks/applies schema migrations; Hibernate validates mappings.

  3. Create configured application beans

    Spring wires controllers/services/repositories and security components. A missing JWT_SECRET can fail startup even after a successful database connection.

  4. Run bootstrap logic and complete startup

    The optional administrator bootstrap creates an admin if needed. Watch the complete result: a Tomcat initialization message alone is not proof that the whole application stayed up.

Build tools versus runtime tools

Maven and the JAR

mvn verify compiles Java and runs configured checks/tests. The Spring Boot packaging step creates an executable JAR with nested dependencies and the application entry point. The root build.py is a workaround for the original Windows folder name ending in a space: it builds a temporary copy and copies artifacts back.

npm, Vite, and dist

npm run build runs TypeScript checking and the Vite build. The result is static HTML/CSS/JavaScript/assets under frontend/dist. Node is used for building and local serving; it does not replace the Java banking backend. Vite preview is a local inspection tool, not a full production hosting setup.

How Docker changes the addresses

The Dockerfile uses a Maven/Java build stage and a separate JRE runtime stage. The application runs as a non-root container user. Compose starts PostgreSQL, waits for its health check, and then starts the API. Within that container network, the database hostname is db, not the Windows machine's localhost.

The Compose frontend is not configured because no frontend service is present in that file. Hosting the built React files and routing /api must be added as a separate deployment concern. The local frontend proxy must point to the Compose backend's 8081 host mapping if that is the backend you choose to run.

Useful vocabulary

API
A defined interface one program uses to request another program's behavior. Here it is HTTP endpoints and JSON shapes.
REST-style endpoint
An HTTP route using resource paths, methods, statuses, and representations. FinCore uses this style for its banking operations.
DTO
A data-transfer shape chosen for the API, independent of the complete persistent entity graph.
ORM
Object-relational mapping: Hibernate maps Java entities/relationships to SQL tables and operations.
JWT
A signed token carrying claims such as identity and expiry. Its payload is not password storage and should not be treated as encrypted secret data.
Database transaction
A unit whose related writes commit together or roll back together. It is different from the application's Transaction entity/record.
Row lock
Database coordination that makes incompatible concurrent access wait or fail according to the locking/transaction rules.
Idempotency key
A caller-supplied instruction identity that lets a retry retrieve the prior result instead of repeating a financial change.
Migration
A versioned database change script, recorded and applied by Flyway.
Proxy
An intermediary. Vite forwards HTTP requests; Spring's transaction proxy intercepts Java method calls. These are different uses of the same word.
React state
Temporary values used to render the interface. It is not durable database persistence.
CI
Continuous integration: automated builds/checks when code is pushed or a pull request is opened.
